# Plugin Studio 向导（L1）

## 什么时候用

- 用户提出任何"我想要/能不能做个…"的开放诉求
- 用户想给 DSH 加功能、自动化、脚本、插件、工作流
- 用户对插件生态、开发方式、可行性提问

## 目的（一句话）

把用户的需求**满足掉**——按成本从低到高：**①本机已装/平台原生 → ②生态现成 → ③自建**。制造是最后手段：用户要的往往是"某个状态被满足"，不是"造一个工具"。

## 两个前置问（第 1 步必问，零实现词汇）

1. **给谁用**：自己用，还是给别人/公众用？
2. **为什么造**：是为了满足自己的需求（工具是手段），还是"自己造一个出来"本身就是目的（练手/学习/享受创造）？

这两个答案决定后面一切：推荐策略、调研深度、合规强度。

| 场景 | 推荐策略 | 调研 | 合规 |
|---|---|---|---|
| 自用 + 满足需求 | 现成优先，能覆盖就不造 | 轻：只查有没有现成 | 松（不发布） |
| 自用 + 享受创造 | **不泼"已有轮子别造"的冷水**——造就是需求；现成件降级为参照样本 | 轻偏中：学形态+防踩坑 | 松 |
| 给别人用 | 先查现成（防重复造）+ **需求验证必做**（生态空缺 ≠ 真实需求，公众场景这是立项前提） | 重：痛点通用性/行业参照/UX | 严（发布质量） |

## 流程

### 第 1 步：听需求
复述"你要的是 X 状态被满足" + 补默认假设（范围/触发/验收——能推断的都写默认值，**明示**在声明里），问两个前置问。产出=需求声明卡，确认门：对/改。
见 `references/requirement-clarify.md`

### 第 2 步：满足途径判断（不是形态选择题）
按 ①已装/原生 → ②生态现成（搜索+审查；**网络失败=明确告知并降级**，不卡流程、不无限重试）→ ③自建 判断。①②能覆盖 → 推荐卡 + 确认，**结束，不造**。只有 ③ 才进自建，且先问一句"为什么现成的不行 / 自建的思路是什么"（防重复造）。
**第①层判断的入口=官方教程+运行时实测**：先读官方 cordis-tutorial / capability-seams 建立「平台到底有什么」的认知（见 `references/official-docs.md`），再用 cordis_inspect 实测确认——文档是线索，实测是证据。
见 `references/ecosystem-scan.md`

### 第 3-5 步：自建路径（只有真缺口才走到这）

3. **形态推导**：向导内部判断（插件/skill/脚本/工作流/preset/看板任务），结论+理由进报告——**不向用户弹形态菜单**。
   见 `references/form-selection.md`
4. **调研 + 方案合规**：分类调研（平台能力/同生态/行业参照/工程实践；需求验证按前置问决定做不做）→ 方案报告 + 合规核对（强度按场景分级）。
   见 `references/ecosystem-scan.md`、`references/compliance.md`
5. **拍板 + 交付**：一句话方案 + 验收标准 → 用户拍板 → 按选定形态落地。
   见 `references/scaffold.md`

## 呈现方式（判断归向导，不新造 UI）

- **简报**：每步结论以文本输出（工具已声明 present* 卡片意图，当前 Web UI 不渲染 generic card——平台边界实测；声明保留，待 UI 支持自动生效）：需求声明 / 满足途径判断 / 形态推导 / 调研分栏 / 方案。
- **确认门**：`ask_user_question`，只有"对 / 改"两个按钮（实机可弹）——**不做方向菜单、不做问卷**。
- 判断归向导，授权归用户：用户全程最多三次发言（说想法 → 确认需求声明 → 拍板方案）。
- 长报告进文件（回复轻量化），对话只留简报 + 确认门。

## 铁律

- **原生能力优先**：开发前盘点 DSH 原生能力/现有组件，能复用绝不开发——只补缺口（反例：开新对话执行任务是 runner 原生能力，不需要自研）。**注意归属**：本机已装的第三方插件 ≠ 平台原生；下"原生"结论前查运行时包清单（`@deepseek-ai/dsh-*` 才是平台原生），静态文档标注可能过期。官方给教程（cordis-tutorial/cookbook/capability-seams，见 `references/official-docs.md`），maker 是把教程机器化——第①层判断先读官方教程入口，再用 cordis_inspect 实测。
- **用户提出的方案只是候选**：先澄清真实需求，再评估方案是否合理。
- **先调研后动手**：同生态已有 → 直接用；有空缺才自研。
- **写代码前先读契约**：tool 参数 schema、client 自注册格式、host ESM 等，动手前查运行时/现成源码，不凭记忆（反例 2026-08-27：required:false 导致启动崩溃）。
- **交付前过合规清单**；改动 profile/preset 组合前先加载 `editing-cordis-compositions` 技能。
- **回复轻量化**：长内容进文件，对话里只留结论。
- **派发 prompt = 目标 + 产出 + 完成判据（不教方法）**：方法论是 agent 的能力；prompt 只说"要什么、产出什么、关键线索"，并给出**完成判据**（拿到哪几类证据/交付物即停）。反例 2026-08-27：调研任务无完成判据 → 无界深挖停不下来。
- **跨对话提 issue（AI 是观察者，不是修理工）**：遇 bug/流程问题 → 提详尽 issue（现象/复现/影响/根因/建议修复方向）；重要 bug 一条一文件进本仓库 docs/bugs/，小坑一行进 PITFALLS（retro_learn，装 dsh-retro 时；未装则只提 issue）；不自行修复、不静默绕过——修复 = 人授权的新任务。
- **修 bug 同一 commit 更新 docs**：重要 bug 在仓库 docs/bugs/ 一条一文件（用模板）；不更新文档不算修完。
- **逐步暴露（渐进式披露）**：顶层只给"何时用 + 入口/下一步"，细节进引用、用到才加载；不把整套规范一次性注入（反例：开发规范全塞进系统注入段）。
- **自我指涉幻觉（plugin 场景固有陷阱）**：AI 在 DSH 上开发 DSH 插件，开发对象=运行宿主，天生容易把自己当「外部部署目标」。重启/杀 DSH、改 harness 源码、改/删 cordis preset、卸载自己正依赖的插件，都是**自杀操作**——动手前问一句「这东西在跑我吗？」是 → 交回人类；「停→启」类操作必须原子化。
- **网络降级**：生态搜索（npm/GitHub/市场）失败时，明确告诉用户"网络不可达，本机已装的没有现成——可走自建路径或稍后重试"，不无限重试、不卡流程。
