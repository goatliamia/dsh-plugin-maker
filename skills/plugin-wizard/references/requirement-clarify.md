# 听需求（第一步）

> 目标：听懂"他要创建/满足的是什么"，不是让他答问卷。用户只说想要什么，判断归向导。

## 两个前置问（必问，零实现词汇）

1. **给谁用**：自己用，还是给别人/公众用？
2. **为什么造**：要满足自己的需求（工具是手段），还是"自己造一个出来"本身就是目的（练手/学习/享受创造）？

这两个答案决定后面一切：推荐策略、调研深度、合规强度（对照表见 SKILL.md「两个前置问」节）。

## 复述 + 默认假设

- 把用户的方案**翻译回需求**："你要的是 X 状态被满足"，不许用实现词汇。
- 能推断的**给默认值并明示**，不让他填空：范围（本机哪些目录/仓库）、触发（定时/事件）、验收（提醒一次/零打扰）、不做（自动提交之类）。推断错了用户纠正一次，成本远低于让他从零描述。
- 反例对照：用户说"记个便签" → 需求是"轻量+可见+跨会话续接"，不是"建个 markdown 文件"；用户说"做个划选引用" → 需求是"指向不搬运、一次点击"，不是"复制全文加前缀"。

## 输出：需求声明卡

格式（简报卡，`presentResult` → generic card）：

```
📋 需求声明
为 <谁> 解决 <问题/满足什么状态>
默认假设：范围 <X>；触发 <Y>；验收 <Z>
不做 <W>
（前置问答案：自用/他人 × 满足需求/享受创造）
```

确认门：`ask_user_question`「需求声明对吗？」——只有 **对 / 改** 两个按钮。用户说"改"，只问改哪一条，不从头再问。

## 不做

- 不给形态菜单、不给"推荐方向"选项——方向是向导判断的，不是用户选择题。
- 不在需求没确认前进入任何调研或实现。
