# 满足途径判断 + 分类调研（第二步 / 第四步）

## 满足途径三层（第二步，自建前必经检查）

按成本从低到高，每一层**先查后判**，结论进"满足途径卡"：

1. **本机已装 / 平台原生**（零网络）：已装插件清单 + 平台原生能力（todo/goal/schedule/workflow/jobs…）。能满足 → 直接指给他用，**结束**。
2. **生态现成**（需网络）：npm 搜索、GitHub topic/awesome 列表、DSH 市场。有现成 → 审查后推荐安装，**结束**。
3. **自建**（最贵）：只有真缺口才走到这。先问一句"为什么现成的不行 / 自建的思路是什么"（防重复造；享受创造场景不泼冷水，陪造，现成件当参照样本）。

**网络降级**：生态搜索失败 → 明确告知"网络不可达，本机已装的没有现成，可走自建路径或稍后重试"——不无限重试、不卡流程、不把"搜不到"当成"没有"。

## 分类调研（第四步，自建路径内）

> 每类只回答一个问题，结论分栏记录进调研卡。

1. **平台能力（原生优先，最重要）**：官方给不给？**用运行时查询**——cordis_inspect（Service/Slots/Event）、运行时包清单、源码调用链；能复用原生绝不开发，只补缺口（不依赖静态文档，静态文档标注可能过期）。→ 可行性 + 挂载点
2. **同生态**：轮子是否已存在？（GitHub topic / awesome 列表 / npm）→ 装/不装 + 协议借鉴
3. **行业参照**：最成熟形态是什么？能否移植？（Codex/Cursor/Obsidian 等，不限 DSH）→ UX 模式
4. **工程实践**：同类项目怎么做工程？（CI/测试/发布）→ 规范借鉴
5. **需求验证**：痛点通用吗？（issue 区/star）——**按前置问决定**：自用+满足需求/享受创造 → 跳过；给别人用 → 必做（立项前提，生态空缺 ≠ 真实需求）

## 执行顺序

满足途径三层判断在前；进入自建后 ① → ② → ③（④⑤ 贯穿；⑤ 公众场景立项前必做）。
调研结论带承接：结论之后做什么动作、固化到哪，不含糊留白。
