# 五步分类调查（research）

## 什么时候用

- 用户说「调查/调研/看技术可行性/有没有能力做」等触发词
- 用户想给现有系统加功能前的可行性评估

## 硬约定

- 五类缺一不可，按类分栏汇报（每一类给结论，不是抄素材）
- 调查产出=可行性 + 形态判断（该长成插件/工具/守卫/skill/preset/脚本哪种）+ 挂载点 + 成本
- 不写实现代码；用户拍板后才进实现阶段

## 五类（顺序执行）

1. **平台能力**（DSH 官方运行时）：官方给不给这个能力？查 cordis_inspect（服务/事件契约）、官方仓库与文档、本地安装包源码。产出=可行性判断+挂载点清单。
2. **同生态**（DSH 插件圈）：轮子是否已存在？生态的开发哲学是什么？（DSH「一切皆插件」→ 硬约束做进工具/守卫，软规则写文本会失效）。产出=装/不装决策+**开发形式判断**（这东西该以哪种形态存在，由生态特点决定）。
3. **行业参照**（其他 AI 工具）：最成熟形态是什么？能否移植？（Codex/Cursor 交互、CI/lint 规则表等）。产出=UX/架构模式库+移植清单。
4. **工程实践**：同类项目怎么做工程？CI/测试/发布/版本策略。产出=工程规范借鉴。
5. **需求验证**（独立维度）：自用 → 跳过；面向公众 → 立项前单独做（issue 区、社区讨论、star 分布）。

## 铁律

- 挂载点必须查运行时契约（cordis_inspect），不凭记忆（反例：tools/result 的 dispatch 根 ctx 收不到，post-execute 才全工具触发——都是实测出来的）
- waterfall 事件监听器必须无条件 return next()（坏监听器锁死全部工具，只能重启）
