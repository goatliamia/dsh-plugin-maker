# Maker 定位文（2026-08-29，开源前定稿）

> 作者手记全文留档。README 的「为什么需要它 / 核心原则 / 边界 / 为什么开源」各节是它的浓缩版。

---

## 一切皆插件，但不是所有人都是插件开发者

DeepSeek Harness 有一个非常有吸引力的理念：**Everything is a Plugin.** 一切能力都可以被组合、替换、扩展。工具是插件，Skill 是插件，Session 有自己的组合方式，甚至整个 Harness 的很多能力都可以通过插件重新组织。这个理念的魅力在于，它把原本属于平台内部的东西，逐渐变成了开发者可以触碰的东西。

但真正开始用以后，一个很现实的问题很快出现了：**如果一切皆插件，那么是不是所有人都需要成为插件开发者？**

我第一次真正意识到这个问题，并不是因为 AI 不会写代码。恰恰相反，它会写。有一次，我让 AI 帮我开发一个 DSH 插件。开发过程中，它根据一个对普通软件开发者来说完全合理的思路修改了运行环境，然后尝试重启。结果，它把自己卡死了。

这不是简单的代码错误。它对"怎么开发软件"的理解甚至没有错。真正错误的是，它在行动规划中把自己当成了一个站在系统外部的开发者，而没有正确理解自己与运行环境之间的关系。它不仅可以写代码，还可以改变自己工作的环境。

于是一个新的问题出现了：**当 Agent 获得了扩展 Harness 的能力以后，我们真正需要解决的，还是"它会不会写代码"吗？** 我后来越来越觉得，不完全是。真正的问题是：**它是否知道应该做什么、不应该做什么，以及哪些事情根本不值得重新做一遍。**

## 一切皆插件之后，代价也一起出现了

插件化解决的是自由度。但自由不是没有成本的。当系统从"平台替你决定一切"，变成"能力都可以被自己组合"，很多原来由平台承担的工作，就转移给了使用者。你需要开始判断：这个需求到底是什么？Harness 原生已经支持了吗？社区里有没有现成插件？这个插件是否真的适合拿来用？这个接口现在到底是什么？哪些配置是固定契约？当前这个改动会影响谁？DSH 更新以后，这个插件还会不会继续工作？

对于一个人类开发者来说，这些只是工程工作。但对于 Agent 来说，这意味着它会反复做大量探索：读文档 → 查源码 → 找例子 → 猜 API → 写一点 → 跑一下 → 出错 → 再查 → 再试。这当然能够完成任务。问题只是：**为什么每一个 Agent，都要重新支付这一遍认知成本？**

## 所以我开始做 Maker

Maker 最初只是一个很朴素的想法：把 DSH 插件开发过程中那些反复出现的、机械的、容易出错的工作拿出来。后来它逐渐变成了一个插件开发工坊。但我现在更愿意把它理解成：**一个用于管理"插件化自由"带来的工程成本的工具。** 它不是单纯帮 Agent 写插件。它更关心：**这个东西到底应不应该成为插件。**

## 在写之前，先问一次：真的需要写吗？

Maker 最重要的原则之一，是 **Reuse before invent.** 当一个需求出现时，第一步不是生成代码，而是先判断：本机已经有？→ 生态已经有？→ DSH 原生已经支持？→ 行业里有没有更成熟的做法？→ 最后才是：值得不值得自己造？因为开放生态最容易出现的一个问题，就是插件越来越多，但真正需要的能力并没有越来越清楚。

所以 Maker 有时候最重要的结果，不是"这是一个新插件"，而是"不用做，底座已经解决了"。这也是为什么 Maker 的一个重要理念，来自真实开发中的一个很简单的发现：**一个好的开发工具，不应该只会告诉 Agent"怎么做"，还应该允许它明确地说"不需要做"。**

## 把不值得消耗模型智能的工作，拿出模型的自由生成

开发插件时，有很多事情实际上并不需要 AI 自己决定。比如固定的目录结构、入口形式、导出要求、某些 bundle 配置、已经验证过的 API 契约。如果这些东西每次都让模型自己写，那么每次都存在重新犯错的可能。所以 Maker 采用了一条很简单的原则：**模型负责需要判断的事情，确定性机制负责不值得消耗模型智能的事情。**

于是就有了：**Scaffold**（生成已经验证过的插件骨架，而不是让模型从空目录开始猜）、**Check**（把已经知道的 Harness 契约变成静态检查）、**Vet**（面对第三方插件时，先检查它是否符合当前运行环境，而不是直接接进去再试错）、**Adopt**（对于少量安全、确定性的修改，直接自动应用，而不是让 Agent 自己重写）、**Impact**（变更之前扫描引用关系，减少"我好像没影响到其他地方"的猜测）、**Upstream**（DSH 自身还在快速变化，所以插件不应该假设今天能运行，明天就一定能运行）。

这些东西都不是凭空发明的。Scaffold 在传统软件工程里早已有成熟先例。Static check、codemod、dependency update、change impact analysis，也都不是新概念。真正有意思的地方在于：**这些成熟的软件工程方法，现在开始被重新放进一个可以自主行动的 Agent Harness 里。** 传统软件工程通常默认：人知道该怎么做，只是需要工具帮他做得更快。Agent 工程则开始出现另一个问题：**Agent 本身也需要被约束在正确的工程路径上。** 这就是 Maker 真正试图解决的地方。

## Maker 甚至不是从"我想做一个插件"开始的

我后来发现，很多问题根本不是"代码能力"问题。比如：模型记得某个 API，但 API 已经变了；模型知道某种配置以前可以工作，但当前版本已经不支持；模型写出了看起来完全合理的 bundle，却因为一个细小的导出问题让整个能力消失；模型甚至可能在修改自己的 Harness 时，把自己正在运行的环境弄坏。这些问题共同指向一个事实：**Agent 缺少的有时不是智力，而是一个可靠的工程环境。** 于是 Maker 逐渐形成了自己的方向：**不是让模型变得更聪明，而是减少它因为环境不可靠而失去原有能力的机会。**

## 这也是为什么 Maker 不应该吃掉 Retro 和 Reactor

随着开发继续进行，我又发现了另一个问题：如果所有东西都塞进 Maker，Maker 很快就会重新变成一个"大而全"的中台。所以后来我们把几个问题明确分开了。**Maker**：开发期的能力生产、验证和维护。**Retro**：运行以后发生了错误，怎么观察、归因，并判断哪些经验值得沉淀。**Reactor**：多个工作线、多次会话之间，项目状态如何持续存在、传播和收敛。它们可以组合起来，但不应该互相吞掉责任。这其实也再次回到了 DSH 的原始哲学：**Everything is a Plugin.** 不是所有能力都必须塞进同一个插件。

## 一个有意思的变化：Maker 自己也被这些原则约束

Maker 的开发过程本身，也经历过很多次这样的循环：发现问题 → 想增加机制 → 实测 → 发现过度抽象 → 撤回。有些规则甚至在发布以后很快被撤掉。这件事对我来说反而很重要。因为如果一个"帮助别人避免造轮子"的工具，本身不断往系统里添加新的永久机制，那么它最终一定会背离自己的初衷。所以 Maker 后来逐渐形成了一个很简单的倾向：**先查已有能力。能复用就复用。能机械化就不要让模型自由生成。一次现象不足以成为永久规则。一个修改能不做，就不要做。**

## 现在的 Maker

目前的 Maker 已经能够独立安装使用。它包含插件骨架生成、契约校验、第三方插件体检、有限安全修复、开发动作清单、引用面扫描，以及两个面向插件开发的 Skill。但我不太想把它描述成"一个可以自动帮你开发 DSH 插件的 AI"。因为它并不能替代开发者，也不应该替代开发者。它更像：**一个降低 Harness 扩展成本的工程层。** 它帮你决定：要不要做 → 怎么开始 → 怎么避免机械性错误 → 怎么检查 → 怎么接手已有插件 → 怎么面对变化。

## 为什么现在选择开源？

因为到这里，Maker 已经完成了另一件重要的事：**它自己完成了一次解耦。** 开发过程中，它曾经和 Retro、Reactor 深度耦合。但随着边界越来越清楚——Maker 自己负责插件开发，Retro 自己负责运行期错误与经验，Reactor 自己负责项目协同——Maker 现在已经可以独立工作。这意味着下一步继续"闭门造车"，可能反而很难得到新的信息。因为 Maker 接下来真正需要的，不再是作者自己的更多想法。而是：**陌生开发者会怎么使用它？** 他们真正痛的是什么？他们最需要的是 Scaffold、Check、Vet、Research，还是根本没想到的别的东西？这些问题，只有真实生态能够回答。

所以这一次开源，对我来说不是"Maker 已经完成了"。而更像：**"Maker 的内部实验结束了，外部实验开始了。"**

## 一切皆插件之后，我们真正需要什么？

我现在还没有一个最终答案。但我觉得 DSH 提出的"Everything is a Plugin"，可能天然会带来一个新的问题：**当一切都可以扩展以后，如何避免所有人都开始重复扩展同样的东西？** 或者再进一步：**如何让 Agent 拥有很高的环境自由度，同时又不让自由本身变成新的工程负担？** Maker 只是这个问题的一次尝试。它并不试图让所有人都成为插件开发者。恰恰相反。**它希望一个人可以使用一个高度可扩展的 Harness，而不必为了每一个需求，都先成为这个 Harness 的专家。**

也许"一切皆插件"的下一句话，不应该是"那就什么都做成插件"。而应该是：**"先判断什么值得成为插件。"**
